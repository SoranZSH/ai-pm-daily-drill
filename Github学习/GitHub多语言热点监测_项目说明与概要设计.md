# GitHub 多语言热点监测：项目说明与概要设计

版本：1.0  
日期：2026-09-11  
状态：需求共识与概要设计；尚未实施或完成模型验证

## 1. 文档目的与阅读约定

本文独立说明项目背景、目标、核心约束、统计口径、系统组成、输出形式与验证要求。开发者或评审者无需其他对话材料即可理解项目。

“必须”表示核心约束；“建议”表示概要设计中的实施起点；“待验证/待配置”表示尚未确定的技术或数值选择。文中的模型、覆盖率、周期和样例不构成已验证的性能承诺。本文不包含程序已经实现、已经部署或已经具备历史数据的假设。

## 2. 项目背景与目标

用户希望通过运行在本地的程序，定期发现 GitHub 上近期异常走热、值得进一步阅读和学习的公开项目，并收到便于中文阅读的热点信息。

不同自然语言的项目可能具有不同的曝光和增长背景。仅按全站累计 Star 排名，容易忽略体量较小、文档并非中文或英文、但近期表现异常突出的项目。本项目需要覆盖多种自然语言，并在热度评价中考虑这种背景差异。

项目的核心任务是：利用容易获取的仓库信息及本地积累的历史快照，预测项目未来一个固定窗口内的热度增长及其预测上界；实际增长超过事先保存的上界时，将其识别为爆款候选，再生成简洁中文推送。

项目属于个人使用的本地软件与统计分析项目。信息来源面向全球 GitHub 公开仓库，阅读和学习的最终判断由用户完成。不以组织级商业部署为当前范围。

### 2.1 目标用户与使用场景

目标用户希望减少手动浏览多个榜单和多语言仓库的时间，发现超出通常预期的项目增长。用户先阅读项目名称、简短中文介绍和异常依据；感兴趣时打开源项目，使用浏览器网页翻译等工具深入学习。

### 2.2 成功结果

- 程序能够定期采集、积累快照、生成预测、对账实际增长并输出异常候选。
- 热度判断具有可追溯依据，能够回答“预测时知道什么、预计多少、上界多少、实际多少”。
- 对自然语言差异进行建模或校准，不把某一语言的统一绝对阈值直接套用到所有项目。
- 输出简洁中文阅读信息，并提供可直接访问的源项目链接。
- 模型效果、语言覆盖和采集范围均可检查，不将监测样本结果宣称为全站完整结论。

## 3. 核心约束与范围

| 编号 | 核心约束 |
| --- | --- |
| C01 | 程序运行时不调用大语言模型，不依赖云端模型推理。采集、统计建模、调度和推送由本地脚本控制。 |
| C02 | 允许传统统计/机器学习方法，以及用于语言识别、短文本翻译的本地专用模型；“不使用大模型”不等于禁止所有模型。翻译组件仍需先验证可行性。 |
| C03 | GitHub 数据采集需要联网；本地处理不意味着整个系统离线。模型文件可在准备阶段下载，运行时的语言处理应能本地完成。 |
| C04 | 必须区分自然语言与编程语言。GitHub 的编程语言字段不能作为文档自然语言标签。 |
| C05 | 异常检测比较实际增长与预测上界，不能用均值置信区间替代预测区间。 |
| C06 | 预测必须使用预测时点之前可获得的信息，并在观察结果出现之前保存。 |
| C07 | 爆款候选表示相对模型预期的异常增长，不代表技术质量、原创性、可靠性或商业价值已经得到认证。 |
| C08 | 中文内容范围保持简短，以帮助用户了解大致用途为目标，不要求全文翻译、长摘要或自动技术解读。 |
| C09 | 项目名、仓库路径、代码标识和链接保留原样，其余解释性内容使用中文。 |
| C10 | 候选发现不能仅限于既有高 Star 仓库；需要保留发现低体量与非中英文项目的入口。 |
| C11 | 采集缺失、历史不足、语言不确定和翻译失败必须显式处理，不伪造观测或说明文字。 |

当前范围包括公开仓库发现、历史快照、自然语言识别、热度预测与校准、异常记录、中文简短介绍、定期报告与通知。

当前不要求全文翻译、自动阅读理解整个代码库、代码质量认证、自动运行发现的仓库代码、多用户服务、商业化平台或保证覆盖全 GitHub。模型选择、通知渠道和固定数值参数尚未最终确定。

## 4. 术语与统计对象

| 术语 | 本项目含义 |
| --- | --- |
| 自然语言 | README、描述等人类文本使用的语言，如日语、俄语、英语；不推断作者国籍或用户群体。 |
| 编程语言 | 仓库源码使用的语言，如 Python、JavaScript，作为独立属性。 |
| 监测池 | 当前实际采集和跟踪的仓库集合；不是全站总体。 |
| 热度主目标 | 固定未来窗口内的 Star 净增量。Fork 等可作为预测特征或辅助指标。 |
| 预测上界 U | 给定预测时已知信息，对未来单个观测的单侧上预测界。若界面称 UCL，本文统一按此含义解释，不默认套用控制图的三倍标准差规则。 |
| 爆款候选 | 数据有效且实际增长高于事先保存的预测上界的项目事件。 |
| 推送结果 | 异常候选经排序、去重和通知策略筛选后的用户可见信息。并非所有候选都必须即时通知。 |

建议第一版采用未来 24 小时 Star 净增量为主目标，7 天增长作为辅助展示；最终周期可配置，但预测与实际对账必须使用同一口径。

设项目 i 在时点 t 的累计 Star 为 S(i,t)，预测窗口为 h，则：

```text
实际目标 Y(i,t,h) = S(i,t+h) - S(i,t)
预测信息 X(i,t) = 截至 t 已知的特征
点预测 = 对 Y(i,t,h) 的预测值，需记录其为均值还是中位数等口径
预测上界 U(i,t,h) = 对 Y(i,t,h) 的单侧上预测界
异常条件 = 有效观测且 Y(i,t,h) > U(i,t,h)
超界幅度 = Y(i,t,h) - U(i,t,h)
```

Star 净增量可能为负；不能未经处理就套用仅允许非负计数的分布。快照差值表示净变化，不代表新增 Star 事件总数。

单侧覆盖率为 1−α 的含义，是目标观测在适用数据分布下被上界覆盖的比例目标；它不是项目“是爆款”的概率，也不自动保证各语言、各规模组分别达到相同覆盖率。宽上界必须由数据与校准支持，不能为减少报警任意放宽。

## 5. 数据获取与语言识别

### 5.1 候选发现与跟踪

以 GitHub 官方接口为主要数据来源。建议通过创建时间、主题、编程语言、不同规模范围及多语言关键词等组合扩大候选覆盖，随后持续跟踪已发现项目。

发现策略必须记录查询条件、时间、分页或截断情况及发现来源。对接口限额、搜索结果限制和失败进行处理。语言校正不能修复候选池中完全缺失的项目，因此需要审查不同语言的发现量和低 Star 项目的进入情况。

监测池准入、退出和再发现规则须配置化并留痕。不能在回测时只保留最终走红或仍然可访问的仓库。排名和分位数如有展示，限定为对应监测样本内的结果。

### 5.2 最小数据集合

| 数据 | 用途与记录要求 |
| --- | --- |
| 仓库稳定 ID、名称、URL | 标识与去重；重命名不应变成新项目。 |
| 创建时间、最近推送时间 | 项目年龄与活动特征。 |
| Star、Fork 等数量 | 定期快照与规模特征；保存实际采集时间。 |
| 编程语言、Topics、描述 | 分类、建模候选特征及中文简介来源。 |
| README 有效文本或所需片段 | 自然语言识别与缺少描述时的短文本提取；记录来源版本或内容哈希。 |
| archived、可访问状态等 | 状态处理与异常解释。 |
| 请求状态、采集时间、发现渠道 | 质量检查、覆盖说明与重试依据。 |

仅保存任务需要的信息。GitHub 凭据置于环境变量或本地凭据机制中，不写入仓库、报告或日志。

### 5.3 自然语言识别

先清除代码块、徽章、URL 等干扰，再对描述及 README 正文识别语言。多语言文档记录默认文档语言、其他可用文档语言及识别可靠性；混合内容可按段落识别。

短文本或冲突证据不足时保留“不确定”状态。语言标签表示文档属性，不能据此声称项目属于某国家或社区。是否使用 fastText 等工具及其模型版本，由实际样本验证后确定。

## 6. 预测模型与异常识别

### 6.1 候选特征

- 预测时的 Star、Fork 规模。
- 项目年龄、距离最近推送的时间。
- 预测时之前 1、7、28 天等窗口的增长历史；窗口为建议配置。
- 文档自然语言、编程语言、主题。
- 星期、有效观测间隔和缺失情况。

每个特征必须可追溯到预测截止时点。仓库属性发生变化时，回测使用当时版本，不以今天属性回填历史。结果窗口内的信息不得作为该窗口预测输入。

### 6.2 语言差异与模型结构

模型需允许不同自然语言的预期增长和波动有所区别，同时考虑项目规模、年龄和自身趋势。建议共享整体规律，并允许语言效应或分组校准；样本少的组适当借用整体信息，避免每种语言独立训练造成不稳定估计。

模型家族不在本文锁定。先建立可解释的简单基线，再比较能输出预测上界的方法，例如分位数回归或经适当校准的预测模型。复杂模型只有在时间回测中体现实际收益，才应替代基线。

需要单独审查小语种区间是否过宽、是否几乎无法报警。样本不足时明确标记，不声称已验证其覆盖率或精确尾部概率。

### 6.3 冷启动与数据有效性

新发现项目没有足够历史时，可以使用仅依赖已知属性的冷启动模型，前提是该模型经过对应验证；否则仅展示观察信息并标注“历史不足”，不生成伪精确预测。

电脑关机、联网失败或 API 错误造成的观测缺口不能视为零增长。24 小时窗口若没有合格的终点观测，应按事先定义的时间容差判断；不合格则标记不可评估，或进入另行定义并验证的可变窗口流程，不能把数日增量当作 24 小时增量。

### 6.4 上界校准与回测

按时间顺序划分训练、校准和评估阶段，模拟真实的“先预测、后观察”。如果标签窗口重叠，划分边界需隔离尚未结束的标签，避免跨边界泄漏。模型重训只能使用结果窗口已结束的数据。

评价至少包括整体及主要语言/规模/年龄组的覆盖率、上界宽度、有效样本量、报警数量、重复率和人工阅读价值。罕见尾部的覆盖率评估需展示样本不足带来的不确定性。

如采用共形预测，需要考虑时间相关与分布漂移，不能直接宣称普通交换性假设下的保证适用于本任务。自然语言分组覆盖需实测，不能由整体覆盖率推出。

### 6.5 候选与通知分离

越界事件先落库，再由推送策略选择。排序可使用超界幅度、实际增量和持续增长信息。最小实际增量、通知条数和同一仓库冷却期均为待配置参数，不改变已记录的越界事实。

大量仓库和重复时间窗口会产生大量比较。即使单项上界校准良好，也不代表整体误报率受控。需要监测每日报警负担；若要声称正式的误报控制，必须另外定义检验、误差目标和适用假设。通知条数上限只是阅读负担控制，不是统计误报控制。

## 7. 中文输出与翻译范围

中文输出的目标是让用户快速知道项目的大致内容方向。最小内容单元为“原项目名＋一句中文用途说明”，不要求生成新的总结或解释。

建议文本来源顺序：

1. 仓库已有且对应当前内容的中文简短说明。
2. 对 GitHub description 进行本地翻译。
3. 描述缺失时，抽取 README 第一条有效介绍句进行本地翻译。
4. 无可靠内容或翻译失败时显示“暂无可翻译简介”，保留源项目链接。

单纯翻译自造品牌名不能保证传达用途，因此项目名保留原样。译文标明“本地机器翻译”；如果经过中间语言转译，应记录该路径。保护代码标识、数字、版本和 URL，检查占位符完整性；这些检查不代表语义已获人工认证。

本地短文本翻译先做可行性评估，工具、语种列表、直接翻译/转译路线及资源消耗均待验证。翻译失败不得阻塞热度识别；系统仍输出中文指标、异常理由和明确的缺失说明。用户通过源网站及网页翻译工具完成深入阅读。

## 8. 系统概要设计

建议技术起点为 Python、本地 SQLite、Windows 任务计划程序与本地 HTML/Markdown 报告。它们是实施建议，尚不代表已部署。桌面通知或其他推送渠道通过独立适配器接入，具体渠道待配置。

```text
定时调度
  → 多入口发现 / 已有仓库更新
  → 数据校验与快照保存
  → 结算已到期预测，记录实际结果和越界事件
  → 截止当前时点的特征构建
  → 生成并保存下一窗口预测
  → 候选排序、去重、短文本中文处理
  → 报告生成与通知

历史有效数据 → 定期训练 / 时间回测 / 校准 → 版本化模型
```

| 模块 | 主要职责 | 主要输出 |
| --- | --- | --- |
| 调度与运行管理 | 定时启动、运行锁、失败恢复、配置读取 | 运行记录 |
| 发现与采集 | 查询候选、更新仓库、遵循限额并重试 | 元数据与快照 |
| 语言处理 | 文本清理、自然语言识别、短文本翻译 | 语言标签与中文短句 |
| 特征与模型 | 构建时点特征、训练、预测、版本管理 | 点预测与预测上界 |
| 评估与事件 | 到期对账、数据有效性、越界判断 | 实际标签与异常事件 |
| 报告与通知 | 排序、去重、模板渲染、渠道发送 | 中文报告与发送状态 |
| 质量监测 | 覆盖率、缺失、漂移、报警负担 | 诊断指标 |

### 8.1 最小逻辑数据结构

| 实体 | 必要内容 |
| --- | --- |
| 仓库及属性版本 | 稳定 ID、URL、描述、分类、自然语言及生效/观测时间 |
| 快照 | 仓库 ID、实际时间、Star/Fork、采集状态 |
| 预测 | 仓库 ID、预测时点、目标窗口、特征截止时间/版本、模型版本、点预测、上界、覆盖水平、冷启动状态 |
| 结果 | 关联预测、实际终点、实际增量、有效性和原因 |
| 异常事件 | 关联预测与结果、超界幅度、后续状态 |
| 翻译缓存 | 原文哈希、源语言、目标语言、模型/路径版本、译文、状态 |
| 通知 | 事件或报告 ID、渠道、幂等键、尝试次数、发送结果 |
| 运行与模型版本 | 配置版本、训练/校准截止时间、回测摘要、错误日志 |

预测记录保存后不因重训覆盖；修正需保留版本关系。翻译缓存随原文或模型版本变化失效。重复运行不得重复插入相同逻辑事件；通知重试需考虑发送成功但回执丢失的情况，不能无条件反复发送。

### 8.2 本地运行边界

- 电脑开机、联网且调度可运行时才能正常采集；关机期间无法即时监测。
- 恢复后补跑任务，但对缺失时段遵循数据有效性规则，不补造快照。
- 接口失败、限额耗尽和翻译失败分别记录，不能表现为“没有热点”。
- 无异常时输出明确的“本次没有满足条件的候选”；通知是否静默由配置控制。
- 仓库文本按不可信内容处理，报告进行转义；不执行 README 内命令或下载项目代码运行。
- 模型和数据均保存版本与备份恢复所需信息，避免模型更新后失去结果解释能力。

下列标准定义未来实现需要提供的验证证据；当前文档交付不代表程序已经通过这些检查。数值性能门槛需在试运行数据基础上确定。

| 检查项 | 验证要求 |
| --- | --- |
| 端到端流程 | 能从采集到预测、到期对账、异常记录、中文报告完成一次完整运行。 |
| 时点正确性 | 任一预测的输入均不晚于预测截止时间，训练标签在训练时已经结束。 |
| 区间口径 | 使用单个未来观测的上预测界；标明名义覆盖水平并提供回测覆盖。 |
| 增量口径 | 负净增量、缺失快照和不规则间隔均有明确且正确的处理。 |
| 多语言处理 | 自然语言与编程语言分开；混合/不确定语言可表达，小样本不伪装为充分证据。 |
| 采集覆盖 | 可查看候选来源、截断和语言分布；存在低体量项目的发现入口。 |
| 模型实用性 | 与简单基线比较，展示覆盖、宽度、报警负担和抽样阅读价值。 |
| 推送一致性 | 卡片数字可回溯至预测和快照；去重、冷却及重试行为可验证。 |
| 中文可读性 | 有短句来源和翻译状态；失败可降级，名称和链接不被破坏。 |
| 运行恢复 | 关机缺口、接口失败、重跑和发送异常不产生伪数据或无控制重复通知。 |
| 可复现性 | 给定数据、配置和模型版本，能复核同一预测结果及异常判定。 |

## 10. 实施顺序与待确定项

建议按依赖顺序推进：

1. 建立采集、快照和质量日志，验证多语言候选发现及短文本处理可行性。
2. 积累真实历史数据，建立简单基线和按时间推进的回测流程。
3. 验证预测上界及不同语言的表现，确定可上线的模型与参数。
4. 接入中文报告、候选筛选和通知渠道，完成恢复与重复运行验证。
5. 持续监测覆盖率、采集偏差和阅读价值，按版本更新模型。

历史积累期不能宣称已经具备可靠的尾部预测能力，具体所需样本量由模型与目标覆盖水平决定。

| 待确定项 | 决定依据 |
| --- | --- |
| 采集频率、监测池规模和 API 使用配置 | 接口可用性、配额、设备和覆盖需求 |
| 主预测周期及观测时间容差 | 数据连续性与用户阅读节奏 |
| 上界覆盖水平、校准窗口和重训频率 | 时间回测、漂移、上界宽度与报警负担 |
| 模型家族及语言分组/共享方式 | 基线比较与分组验证 |
| 最小推送增量、通知条数与冷却期 | 阅读负担和候选价值 |
| 本地语言识别与翻译工具、支持语种 | 真实短文本样本、性能与安装可行性 |
| 具体通知渠道、推送时间与时区 | 用户使用方式；内部时间建议统一保存为 UTC |

这些未定项不改变核心目标：通过本地自动化和可验证的预测上界，发现多语言公开项目中超出预期的增长，并提供简短中文入口供用户进一步学习。
