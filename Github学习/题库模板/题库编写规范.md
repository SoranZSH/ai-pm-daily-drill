# 题库编写规范 v2.2 · 每日一题（AI 产品经理知识题库）

写题（无论是人还是 AI）都按本规范。更新题库只需三步：

1. **生成**：把 `出题提示词_重建题库.md`、`出题提示词_采集包.md` 或 `出题提示词_通用PM.md`（产品通用轨）连同本规范、`题库更新_模板.json`、`../知识地图.json`、`../题库目录.md` 一起交给 AI。AI 按提示词分步工作：先出规划表，确认后再按领域逐批写题。
2. **审阅**：用 `审题提示词.md` 让另一个新对话独立审一遍，再按第九节「审阅清单」抽查。
3. **导入**：文件改名为 `题库更新_YYYYMMDD.json`（同一天多份加 `_2`、`_3`）放到 **Github学习 根目录**，双击 `题库更新.exe`，选择【增量添加】或【题库覆盖】，看预览后确认。

题库本体在 `Github学习\当前题库\`，**不要手改**；`题库目录.md` 由 exe 每次导入后自动生成，是给出题者看的现有题目清单。

> **v2.1 新增**（2026-10-12）：为配合新的解析界面，每道题新增「对答案层」字段 `gist`、`points`、`a_pairs`，「讲透层」字段 `basics`、`pitfalls`、`walkthrough`、`method`，并扩展 `key_phrases`（加 `type`、`usage`）。格式仍是 `interview-bank-update/v2`。exe 已支持这些字段：会让解析页显示错乱的问题（类型不对、内容为空、`a_en`/`a_cn` 与 `a_pairs` 拼不上）会拦下导入，其余（条数、字数、深度字段缺失、摘录在原文里找不到）只作提醒。旧题没有这些字段照常导入，解析页自动退回整段显示。

> **v2.2 新增**（2026-10-31）：题库分为 **AI 轨**（01–10）和**产品通用轨**（11–19：需求、业务架构、信息系统、数据、增长与客户成功、战略、设计、交付、立项与生命周期）。新增领域无需改动 exe 与每日一题主程序；通用轨的素材来自 `../素材库/` 的素材卡，规则见 `通用PM领域_扩展方案.md`、`知识搜集方案.md`、`碎片内容整合规则.md`。

## 一、题库定位

这是一个**面向 AI 产品经理的知识题库**，分 AI 轨和产品通用轨，目标读者是想成为 AI 产品经理、但缺少程序员底层基础的人。每道题帮他做到两件事：**真正理解一个知识点**（能讲清是什么、为什么、怎么用），以及**积累能直接说出口的英文表达**（能用英文在 60–90 秒内讲清楚）。

- 题目是**可迁移的知识、思想、方法、案例**，不是某个产品或仓库的阅读理解。
- 开源项目、产品只作为**素材和例证**：可以在回答里用它说明一种方法，但要讲清楚它代表的通用做法，而不是复述它的 README。
- 解释从定义讲起，用业务能听懂的话解释技术，避免堆砌术语。

### 四种题型 `kind`

| kind | 中文 | 问的是什么 | 例子 |
|---|---|---|---|
| `knowledge` | 知识 | 是什么、怎么运作 | 什么是 KV Cache？它为什么能加速推理？ |
| `idea` | 思想 | 为什么这样设计、背后的取舍和理念 | 为什么说上下文工程比提示词工程更接近 Agent 开发的本质？ |
| `method` | 方法 | 怎么做、步骤和判断标准 | 如何为一个 RAG 系统设计离线评测集？ |
| `case` | 案例 | 用一个真实产品或项目说明一种做法 | 以一个开源编码智能体为例，说明它如何拆分规划与执行 |

- `q_cn` / `q_en` 中**不得出现具体仓库名或产品名**，`kind=case` 除外。
- 一个领域内四种题型都应出现；基础题以 knowledge 为主，拓展题以 idea / method / case 为主。

## 二、层级与前置（最重要）

为了保证「先学基础、再学拓展」，每道题都有层级和前置关系。每日一题**只在一道题的前置题全部练完后才推送它**。

| 层级 | `level` | 含义 | 前置要求 |
|---|---|---|---|
| 基础 | `F` | 一个概念/原理本身：是什么、为什么、怎么运作 | 可以没有前置（`"prereq": []`）；也可以依赖别的基础题 |
| 拓展 | `X` | 建立在基础之上的设计思想、方法比较、工程取舍、案例分析 | **必须**至少 1 道前置题，且其中**至少 1 道是基础题 F** |

写作规则：

1. **先规划再写**：先列出本批要讲的基础概念和拓展问题，确认每道拓展题的前置都存在。
2. **前置找不到就先写**：拓展题需要的基础题，如果在 `题库目录.md` 里找不到，**必须在同一个文件里先写这道基础题**，再用临时编号引用它。不允许让拓展题依赖一个不存在的基础。
3. **前置要真的够用**：标为前置的题，应该让一个只学过这些前置题的人能看懂本题。不要只挂一个沾边的题凑数。
4. **拓展题的 `concept` 开头一句**写明「本题建立在 xx（基础概念）之上」，帮读者衔接。这里以及所有正文字段里都**写知识点名称，不写编号**（不写「N2」「AGT-F001」）：导入后临时编号会换成正式题号，正文不会跟着改。前置关系只写在 `prereq` 里。
5. 前置尽量在同一领域内；跨领域可以（例如智能体记忆依赖检索增强里的 Embedding），exe 会提醒你确认。AI 轨与产品通用轨之间也可以互为前置（例如「AI 需求的验收标准」依赖「用户故事与验收标准」），被引用的题必须已经导入。
6. 不要形成循环（A 依赖 B、B 又依赖 A），exe 会拦下。

## 三、编号规则

正式题号由 **exe 在导入时分配**，格式 `领域前缀-层级字母+三位序号`，如 `AGT-F001`、`AGT-X014`。写题时：

| 情况 | 怎么写 |
|---|---|
| 新题 | 写 `"ref": "N1"`、`"N2"`…（同一文件内不重复），**不写 `id`** |
| 修改已有题 | 写 `"id": "AGT-F001"`（原题号）和完整的新内容，不写 `ref`；层级不能改 |
| 删除已有题 | 题号放进分类的 `delete_ids` |
| 引用前置 | `prereq` 里写本文件的临时编号（`N1`）或已有题的正式题号（`AGT-F001`） |
| 导入日期 | **不写** `added`，由 exe 填写 |

导入后 exe 会在 `已导入\` 旁生成「题号对照」文件（`N1 → AGT-F013`）。用过的序号永不回收，覆盖题库后也不会重复。

## 五、解析页长什么样（写题前先读）

答完题后，每日一题的解析页分两层，字段直接对应界面上的位置：

| 层 | 学习者想做的事 | 对应字段 |
|---|---|---|
| **第一层 · 对答案**（10 秒） | 快速知道标准答案的结论和要点，核对自己说到了没有 | `gist` 一句话答案 → `points` 要点自查（逐条勾选「我说到了吗」）→ `a_pairs` 参考答案（逐句中英对照，`key_phrases` 在原文里划线，悬停显示中文） |
| **第二层 · 弄懂它** | 补上看不懂的基础、拆开难点、学会思考方法、积累表达 | `basics` 先补基础概念 → `concept` 本题概念解析 → `pitfalls` 常见误区 → `walkthrough` 难点拆解 → `method` 思维方法 → `key_phrases` 表达积累 → `approach` 答题结构 → `tips` |

基础题的第二层默认折叠，拓展题和「较难」题默认展开。所以**越难的题，第二层越要写透**；基础题的第二层宁可短，不要注水。

## 六、字段要求

### 6.0 每道题的思考顺序（先判断，再填写）

字段不是从上往下依次填的。按下面的顺序想，每一步的产出落到对应字段里：

| 步骤 | 要回答的问题 | 落到哪里 |
|---|---|---|
| 0 定性 | 这道题有标准答案（knowledge，靠**核实事实**），还是有多个合理答案（idea / method / case，靠**判断取舍**）？ | 决定后面把精力放在查证还是论证 |
| 1 定目标 | 学习者学完这道题，应该能说出哪一句话？ | `gist` 就是这道题的成功标准 |
| 2 盘约束 | 读者已经学过什么（前置题）、还缺什么？ | `prereq`、`basics` |
| 3 找关键难点 | 哪一个点最容易想错、或一旦想通其余都顺了？ | `pitfalls`、`walkthrough` 都围绕它展开 |
| 4 想候选 | 有多观点的题，至少想 2–3 个真正不同的答题角度 | 只在规划阶段写出来，不进 JSON |
| 5 取舍 | 用第 1 步的标准比较各角度，选对 AI 产品经理最有用的那个，说清放弃了什么 | 选定的角度决定 `points` 和 `method` |
| 6 骨架先行 | 先定 `points`，再按骨架写 `a_pairs`，最后摘表达 | `points` → `a_pairs` → `a_en` / `a_cn` → `key_phrases` |
| 7 对抗自审 | 站在最挑剔的读者角度，这道题最致命的问题是什么？事实和数字都核对过吗？ | 自检表、独立审题 |
| 8 交付与校准 | 哪些说法自己也不完全确定？ | 输出时列入「不确定清单」，交给审阅者核实 |

**回路**：如果在第 3 步或第 7 步发现问题出在题目本身（问法不对、层级或前置不对、核心结论站不住），应该回到第 1 步重新定题，而不是在字段上修修补补。

### 6.1 字段总表

| 字段 | 必填 | 要求 |
|---|---|---|
| `ref` / `id` | ✅ | 见第三节，二选一 |
| `level` | ✅ | `F` 或 `X` |
| `kind` | ✅ | `knowledge` / `idea` / `method` / `case` |
| `difficulty` | ✅ | `基础` / `中等` / `较难` |
| `tags` | ✅ | 1–3 个中文短标签 |
| `concepts` | ✅ | 1–3 个概念键，从 `知识地图.json` 选（见第七节） |
| `prereq` | ✅ | 列表；基础题可为 `[]`，拓展题见第二节 |
| `q_cn` | ✅ | 中文题目，一句话，口语化；**不超过 34 字**（弹窗会截断） |
| `q_en` | ✅ | 英文题目，以问号结尾 |
| `gist` | ✅ | `{"cn", "en"}` 一句话答案。cn ≤ 40 字，en ≤ 20 词。见 6.2 |
| `points` | ✅ | 3–5 条 `{"cn", "en"}` 采分要点；cn ≤ 30 字；en 是 `a_en` 中**原样出现**的短语。见 6.2 |
| `concept` | ✅ | `{"cn", "en"}`。中文 150–230 字：定义 → 关键机制 → 为什么重要；英文为忠实翻译。拓展题开头一句点明「本题建立在 xx 之上」 |
| `a_pairs` | ✅ | 参考答案的逐句对照：`[{"en", "cn"}, …]`，每个英文句子一项，5–9 项。见 6.3 |
| `a_en` | ✅ | **要背的那段**，120–200 词。**必须等于** `a_pairs` 各项 en 用一个空格依次连接 |
| `a_cn` | ✅ | **必须等于** `a_pairs` 各项 cn 直接依次连接（不加空格） |
| `key_phrases` | ✅ | 4–6 条 `{"en", "cn", "type", "usage"}`；en **原样出自 a_en**。见 6.4 |
| `basics` | 视层级 | 0–3 条 `{"term", "term_en", "explain", "analogy"}`。见 6.5 |
| `pitfalls` | ✅ | 1–2 条 `{"wrong", "why", "right"}`。见 6.6 |
| `walkthrough` | 视层级 | 3–5 个字符串，每个是一步拆解。见 6.7 |
| `method` | 视题型 | `{"name", "steps", "transfer"}`。见 6.8 |
| `approach` | ✅ | 纯中文 80–130 字：采分点 → 推荐结构 → 最有力的落点句 → 会失分的说法 |
| `tips` | ✅ | 30–80 字：必备术语、可复用的落点句、能延伸到哪些题 |
| `source_repos` | 否 | 素材来源仓库 `owner/name` 列表 |

**按层级和难度决定写多深：**

| 字段 | 基础题 F（基础/中等） | 拓展题 X，或任何「较难」题 |
|---|---|---|
| `basics` | 0–2 条，只写题中出现、初学者可能不认识的术语 | 1–3 条，必写 |
| `pitfalls` | 1 条 | 1–2 条 |
| `walkthrough` | 不写（省略该字段） | 3–5 步，必写 |
| `method` | `kind=knowledge` 不写；其他题型写 | 必写 |

**宁缺毋滥**：凡是标「不写」或「0 条」的，没有真正有价值的内容就**整个省略该字段**，不要为了填满而编造。

### 6.2 对答案层：`gist` 与 `points`

- `gist` 是学习者揭晓答案后**第一眼**看到的结论。要能单独成立、直接回答问题，不是「本题考察了……」这类题解腔。好：「缺的是知识用 RAG，缺的是行为方式用微调。」差：「RAG 和微调各有优缺点，需要根据场景选择。」
- `gist.en` 通常就是 `a_en` 的落点句或它的压缩版。
- `points` 是**采分点清单**，学习者会逐条勾选「我说到了吗」，所以每条必须是**可判断有没有说到**的具体论点，不能是「说明了背景」这种空话。
- 每条 `points` 对应 `a_en` 里的一个要点，顺序和 `a_en` 一致；`points.en` 摘自 `a_en` 原文（大小写、标点都一致），界面会用它在答案里定位。
- 3–5 条覆盖整个答案的骨架：一个只记住 points 的人，应该能把答案大致复述出来。

### 6.3 参考答案：`a_pairs` / `a_en` / `a_cn`

- **先写 `a_pairs`，再拼出 `a_en` 和 `a_cn`**：`a_en` = 各项 en 以一个空格连接；`a_cn` = 各项 cn 直接连接。三者必须逐字一致，exe 以后会校验。
- 一项 = 英文的一个完整句子。不要把两句塞进一项，也不要把一句拆成两项。
- `cn` 是**意译**而非逐词硬译：读起来像中国人会说的话，但信息不增不减。
- 英文写法（沿用 v2）：
  - **第一句直接给结论或思考框架**（"I'd start by asking…" / "The core difference is…"），不要 "That's a great question"。
  - 中间 2–3 个要点，用口头路标串起来（first / the second thing / in practice），尽量带一个具体例子。
  - **最后一句是落点**：一句可以单独记住、能复用到别的题的话。
  - 口语化：短句、缩写（I'd, it's, don't），避免书面长从句和生僻词。
  - 事实必须可靠：不编造论文、数据、产品功能；拿不准的数字不写。
  - 举数字例子时先算一遍，确保数字本身正确（例如复合概率、成本估算）。
  - 不说过头话：避免 human-level、彻底解决、完全取代这类绝对化表述，除非确有依据。

### 6.4 表达积累：`key_phrases`

每条四个字段：

| 字段 | 写什么 |
|---|---|
| `en` | 从 `a_en` **原样**摘出的表达（大小写一致），界面会在答案原文里给它划线 |
| `cn` | 中文意思，简短 |
| `type` | 三选一：`词汇`（专业术语或高级词）/ `搭配`（固定搭配、动词短语）/ `句型`（可以换词复用的句子骨架） |
| `usage` | 15–45 字：**怎么用**——什么场合说、能替换成什么、常见易混词或易错点。不要只重复中文意思 |

- 4–6 条里三种 type 至少出现两种；优先选**能迁移到别的题**的表达，而不是只属于这道题的专有名词。
- 摘**短语**，不要摘整句：一般 2–6 个词，换个话题也能用（如 `capped by`、`makes more sense for`）。整句只适合作为 `句型`，而且要能换词复用。
- usage 写**用法**，不写评价：不要「面试必背」「震撼全场」「黄金金句」这类夸张词。
- 好的 usage：「表达取舍时比 is better for 更自然、更委婉」「易混：complimentary 是赠送的、恭维的」。差的 usage：「意思是互补的」。

### 6.5 先补基础概念：`basics`

- 目的：学习者读 `concept` 和答案时，会卡在几个没学过的术语上。`basics` 是**这道题专属的小词典**，提前把这些坎铺平。
- 只收题中实际出现、且一个缺少技术背景的人**大概率不懂**的术语。不要收「数据」「模型」这类常识词，也不要重复解释本题的核心概念（那是 `concept` 的任务）。
- 如果某个术语正是前置题的核心，`explain` 用一两句话快速回顾即可。
- `explain` 40–80 字，用大白话讲「是什么、拿来干什么」；`analogy` 一句生活类比（≤ 30 字），**类比必须在关键点上成立**，宁可不写也不要误导性的类比；`term_en` 写英文术语（缩写附全称）。

### 6.6 常见误区：`pitfalls`

- 写**初学者真的会有**的误解，最好是产品经理、业务方在实际讨论中常说错的话。不要虚构一个没人会犯的「稻草人」错误。
- `wrong`：用第一人称或引语的口吻写出错误想法本身（≤ 40 字）。
- `why`：为什么错，讲清机制或后果（30–70 字）。
- `right`：正确的判断方式，最好是一个可操作的判断规则（30–70 字）。

### 6.7 难点拆解：`walkthrough`

- 面向「看了答案还是不太明白为什么这么答」的人，把**从读题到答出来的思考过程**拆成 3–5 步。
- 每步以动作开头，冒号后说内容，如「拆题：……」「定位：……」「加约束：……」「给顺序：……」。每步 25–60 字。
- 第一步通常是**拆题**：指出这道题表面问什么、实际考什么能力。
- 不是把答案换个说法再讲一遍；要讲清**每一步为什么这样想**。

### 6.8 思维方法：`method`

- `name`：给这道题用到的思考方法起一个短名（≤ 8 字），如「诊断式取舍」「成本—收益—风险三角」。
- `steps`：2–4 个短步骤，每个 ≤ 12 字。
- `transfer`：这个方法还能迁移到哪些问题（30–60 字，举 2–3 个具体例子）。这是本字段最重要的部分。
- 同一个方法可以在多道题里复用同一个名字，便于学习者形成套路。

## 七、概念键

- `Github学习\知识地图.json` 定义了稳定的概念键，如 `rag.embedding`（Embedding 向量表示）、`agt.tool_calling`（工具调用）。
- 每题选 1–3 个最贴切的键。基础题通常就是讲其中一个键；拓展题可以组合多个键。
- 确实没有合适的键时可以新写（格式 `小写领域.小写下划线名`），exe 会提醒「知识地图里没有」；确认后把它加进知识地图。
- 采集程序靠概念键判断「哪些知识已出题」，所以请认真选。
- 新增概念的 `aliases` 会被采集程序用来在 GitHub 项目说明里找概念：不要用 ERP、API、PRD 这类短缩写，只用完整术语，拿不准就写空数组（详见 `碎片内容整合规则.md` 第七节）。
- 产品通用轨的素材来源（书目、标准、经历）记在素材卡上，不写进题目 JSON；`source_repos` 只写 GitHub 仓库。

## 八、JSON 格式坑

- 字符串里**不要用英文双引号**，中文引用用「」，英文引用用单引号 `'like this'`；非用不可写成 `\"`。
- 最后一个元素后面**不要加逗号**。
- 英文答案里别混入中文标点（，。“”），exe 会提醒。
- 文件用 UTF-8 保存。
- 模板里的「说明」字段可以留着，exe 会忽略。
