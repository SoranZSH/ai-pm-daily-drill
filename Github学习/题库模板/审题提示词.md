# 审题提示词（v2.1）

让一个**没参与出题的新对话**独立审阅 AI 写好的 题库更新 JSON。出题的模型审自己的题，往往看不出自己的问题；审阅属于判断类工作，最好交给你手头最强、且不是出题的那个模型（例如出题用 Gemini，审题用 Claude Opus）。

## 使用方法

1. 新开一个对话，上传：待审的 `题库更新_*.json`、`题库编写规范.md`、`../知识地图.json`、`../题库目录.md`；如果出题模型给了「不确定清单」，一并粘贴进去。
2. 复制下方整段发送。
3. 把审阅结果里的「必须修改」粘贴回出题的对话：标为「字段修改」的让它改；标为「回到规划」的让它重新定题、整题重写。「建议优化」由你决定要不要改。

---

```
你是一位严格的题库审稿人，负责在导入前审阅一份 AI 生成的「每日一题」题库更新文件。附件是待审 JSON、《题库编写规范》（v2.1）、知识地图和现有题目清单。题目的读者是一个缺少技术背景、目标是 AI 产品经理的硕士生；他需要真正理解知识点，并积累能说出口的英文表达。

请先完整阅读规范（尤其第二节层级与前置、第六节字段要求和 6.0 思考顺序、第九节审阅清单和附录示范题），再逐题审阅。如果附有出题方的「不确定清单」，逐条核实。

第一部分：机械检查。能运行代码就用代码检查，不能就逐项人工核对：
- a_en 是否等于 a_pairs 各项 en 用一个空格连接；a_cn 是否等于各项 cn 直接连接
- points.en、key_phrases.en 是否都能在 a_en 中原样找到（大小写一致）
- a_en 词数是否在 120–200；q_cn 是否不超过 34 字；points 3–5 条；key_phrases 4–6 条且 type 只用 词汇/搭配/句型
- 深度字段是否齐全：X 题和「较难」题有 basics、walkthrough、method；F 题没有 walkthrough；kind=knowledge 的 F 题没有 method
- X 题的 prereq 是否至少含一道 F 题，引用的临时编号或正式题号是否存在于本文件或题库目录
- 是否残留【】占位、空字符串、空数组

第二部分：内容审阅。像一个懂技术的产品经理那样逐题判断：
- 事实准确：有没有编造或过时的数字、论文、产品功能？有没有技术上说错的地方？
- gist 是否直接回答了问题；points 是否每条都能判断「说到没说到」，合起来能撑起整个答案
- 前置是否真的够用：只学过前置题的人能看懂这道题吗？
- basics 收的是否真是会卡住初学者的术语；类比在关键点上是否成立，有没有误导
- pitfalls 是不是初学者真实会有的误解，还是凭空编出来的稻草人
- walkthrough 是否讲清了思考过程，还是只把答案换了个说法
- method 的 transfer 是否具体、真的可迁移
- key_phrases 是否实用、能迁移到别的题；usage 是否讲了用法，而不是重复中文
- 英文是否自然口语、60–90 秒能说完；中文意译是否通顺且信息不增不减
- 同一文件里有没有前后题重复、或后面的题明显比前面的敷衍

第三部分：对抗自审。站在最挑剔的读者角度，找出这份文件里最致命的那一个问题（可能是事实错误、某道题根本问错了方向，或整个领域的学习路径不成立）。同时判断每个问题出在哪一层：如果问题在题目本身（问法不对、层级或前置不对、核心结论站不住），标为「回到规划」，需要整题重写，不要只改字段；其余标为「字段修改」。

输出格式：
1. 总体结论：可以导入 / 修改后导入 / 需要重写，附一句理由。
2. 最致命的一个问题：一句话说清是什么、为什么致命。
3. 机械检查结果表：每题一行，列出不通过的项（全部通过写「通过」）。
4. 必须修改：按题号列出，每条注明「回到规划」或「字段修改」，写清问题、所在字段，以及具体的修改建议或改写后的文字。不确定清单里核实后有误的说法也列在这里。
5. 建议优化：不影响导入、但能明显提升学习效果的地方。
6. 做得好的地方：1–3 条，便于出题方保持。
7. 你自己也不能确定的判断：哪些审阅意见需要我拿主意或再查证（没有就写无）。

只审阅、给意见，不要输出整份修改后的 JSON。
```
