## 2. 最致命问题（Top 2）

### ① RAG 文件：前置链断裂，几处核心机制讲错（影响 N23–N34 整组）

**前置链断在 N23 / N24。**
- N23 是 RAG 入门题，但它的 concepts 一口气挂了 `rag.chunking`、`rag.embedding`、`rag.vector_db` 三个键，这正是 N24、N25、N26 各自的主键。采集程序会因此误以为这三个概念「已出题」。
- N23 正文写了「转成向量」，却没有解释什么是向量。
- N24（切块）的前置只有 `LLM-F001` 和 `N23`，正文却在用 "We can't embed a two-hundred-page manual"、"one blurry vector"、「向量主题纯度」。讲 Embedding 的 N25 排在 N24 后面，也不在 N24 的前置里。读者在第二道题就会撞墙。

**几处机制讲错，恰好都是面试官最爱追问的点。**
- **N27 RRF 的机制讲反了。** 原文第 6 句 "boosting any passage that ranks near the top in either list"。RRF 实际奖励的是两路排名都靠前（共识）。按 k=60 算：只在一路排第 1 的段落得 1/61 ≈ 0.0164；两路都排第 40 的段落得 2/100 = 0.020，反而更高。
- **N25 向量维度讲错。** "every dimension captures subtle semantic traits" 是典型误解：单个维度没有可读含义，含义来自整串数字。
- **N33 把推断写成了 Onyx 的事实。**
  - "enforces access control inside the index query" 和 "millisecond answers" 在原文里都找不到。原文只有 "pulls data along with metadata, permissions"、"same access controls as the person running them"、"low latency, and low cost"。而且一次完整回答包含 LLM 生成，不可能做到毫秒级。
  - "poll dozens of live app connectors" 也有问题。原文是 "iteratively searching dozens of MCP"；在 Onyx 里，connector 恰恰是后台同步用的组件，这样写和本题第 3 句自相矛盾。
- **N26 夸大全量比对的延迟。** 原文说全量比对 "drags online latency into seconds"，concept 里还有「几秒甚至几十秒」。实际估算：100 万条 768 维 float32 向量约 3 GB，单次全扫约 0.1–0.3 秒，到千万级或高并发时才到秒级。

**风格问题。** RAG 文件明显是另一批生成的，口语感明显弱于其他四个文件：a_en 共 22 个破折号；有 4 处 never/always 式命令句；gist.cn 写成电报体，如「多层导航图微损召回换毫秒响应」「双塔粗排…交叉编码器逐字交互精选前五」。基础题第一眼就是黑话。

### ② N71 放在「业务架构」不成立，和 N45 大面积重复，`biz.org_permission` 实际没人讲

- **领域归属不对。** 资料库原文把 Paperclip 标为 `agent-framework / AGT`。扩展方案第六节规定：给 AI 动作设审批属于 AI 轨的人机协同，通用轨的审批流讲的是企业里的人。
- **和 N45 重复。** N71 第 4 句 "runaway loops can burn through tokens before anyone notices" 与 N45 第 3 句几乎逐字相同；两题的 pitfalls[1] 都是「每一步都设人工审批」，why 和 right 也基本一样；「预算硬上限 + 审批关卡 + 留痕」三件套也重复出现。
- **后果。** 被问到「企业审批流怎么设计」（组织树、岗位与人分离、按汇报线找审批人、会签/或签、转交与离职交接）时，学习者从这一领域里一句都拿不出来。另外，规划里原本有一道 ITSM 案例题被删了，那正是和你 ServiceNow 方向最贴近的一题。

## 5. 建议优化项（不影响导入）

1. **收尾句模板化（系统性问题，强烈建议改）。** 10-31 的四个文件共 49 题，最后一句全部以 "My rule of thumb:"（37 题）或 "Bottom line:"（12 题）开头；RAG 文件 12 题里也有 4 题这样收尾。一场面试被问到 3 道题，就会连说 3 次 "My rule of thumb"，很容易被听出是背稿。建议每个文件至少有一半改成直接说落点，或换用 "So the short version is…"、"If I had to sum it up…"、"What I'd tell the team is…"、"The way I see it…"，a_pairs.cn 同步改。
2. **思维方法名零复用。** 20 个 method.name 各用一次。规范鼓励复用同名方法来形成套路。例如 N30、N32 都是选型题，可以统一用示范题里的「诊断式取舍」；N45、N71、N83 都可以归到「授权三件套」。
3. **覆盖缺口（下一批再补）：**
   - RAG 领域缺「RAG 还是微调」（要先补 `trn.fine_tuning` 的基础题），以及「无证据时如何拒答、引用怎么设计」；
   - 智能体领域缺「如何评估智能体」（成功率、轨迹、成本）和「工具结果里夹带的间接提示注入」，分别归 EVL、SAF；
   - SYS 领域缺「日志、监控、告警」和「缓存」；
   - Kano 的动态性（兴奋型需求会逐渐变成基本型）可以在 N54 里补一句。
4. **全部回答都是「I'd…」的假设语气，没有一句亲历。** 背诵时可以用自己的经历换掉一两个例子，例如用 ServiceNow CSM 流失项目里的访谈和跟岗换掉 N50 的例子、用项目里的基线指标换掉 N58 的例子。亲历的细节最能让面试官相信你。
5. **KP usage 约四成只在复述中文意思，以 RAG 文件最集中**，例如 N23 decoupled pipelines、N26 multi-layer navigation graphs、N28 deep relevance scoring。另外，N28、N29 的「黄金配比」「立刻见效」改为「常见起点」「通常见效」。

## 6. 亮点保留

1. **判断标准式落点句。** N35 的 "use a workflow when you can draw the flowchart, and an agent when you can't"、N44 的 "treat tools as a user interface for the model"、N46 的 "memory isn't storage, it's curation"。一句话就给出可迁移的判断规则，后续领域照这个标准写。
2. **排障决策规则。** N29 的 "If Recall@50 is low, tuning your reranker won't help at all because the right chunk never entered the candidate pool"。把指标直接变成下一步行动，是全批最像产品经理的一句。
3. **一个反例讲透概念。** N69 的 "approval flows digitized with all seven signatures intact, so the only gain is that people wait in an inbox instead of a tray"，以及 N50 的 "a spreadsheet kept on the side because the system can't handle exceptions"。具体画面比任何定义都好背、好讲。
