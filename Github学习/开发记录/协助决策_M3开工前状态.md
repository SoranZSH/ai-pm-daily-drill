## 4. 遇到的问题、建议方案与理由

### P1 电脑端 shell 不可用（阻塞，优先级：高）

- **现象**：T1–T3 全部报 `Workspace unavailable`。
- **影响**：
  - 无法在用户机器执行 `git status` 与提交（P2）；
  - 无法在用户机器运行 Go、Python 测试；
  - 无法执行 `pip install requests`；
  - 无法运行采集程序，M3 第 15 条（真实网络）无法完成；
  - 方案要求的「在用户环境验收」无法达成。
- **建议**：
  1. **先由用户处理**：确认 Claude 桌面应用在线、这台电脑在线；尝试重启 Claude 桌面应用；检查 Windows 上为「隔离 Linux 环境」所需的组件是否可用（错误提示指向的隔离环境，多半依赖 WSL 或虚拟化功能，具体请用户自行检查）。
  2. **若短期无法恢复，采用「容器开发 + 回写」模式**：代码在容器中编写和测试（容器内有 Go 与 Python），再通过 `device_commit_files` 写回 `Github学习\collector\`；每个里程碑结束时，用户在本机再运行一次验收用例。
- **理由**：
  - 不能把容器中的结果当作用户机器上的结果；容器与用户环境在 Python 版本（3.13 对 3.11）、路径、编码、行尾上都有差异。
  - 回写方式只能写文件，不能执行 git，因此提交步骤保留给用户（见 P2）。
- **状态**：待用户处理；需要决策 Agent 或用户确认采用哪种模式。

### P2 M1–M2 改动尚未 git 提交（优先级：中）

- **现象**：方案要求每个里程碑结束提交一次；用户要求先 `git status` 给他看，再提交 `M1-M2: 契约升级（v2 题库格式、题号分配、前置关系）`。由于 P1，无法执行。
- **建议**：由用户在 PowerShell 执行：
  ```powershell
  cd D:\Download\面试英语题库\Github学习
  git status
  ```
  检查输出（确认 `题库备份\`、`已导入\`、`题号登记.json` 等是否应该入库），然后：
  ```powershell
  git add -A
  git commit -m "M1-M2: 契约升级（v2 题库格式、题号分配、前置关系）"
  ```
- **理由**：
  - 不手改 `.git`，避免索引或对象损坏。
  - `git add -A` 之前必须看 `git status`：`.gitignore` 目前是否包含 `state.db`、`采集包\`、`采集日志\` 要到 M3 才会要求，而不是现在。
- **状态**：待用户执行。

### P3 方案矛盾：M3 依赖 M5 才定义的方向词表（优先级：高，需决定 Q1）

- **现象**：
  - M3.1 文件表中，`方向词表.json` 标注为「M5，附录 D」；
  - M3.7 发现阶段要求「t 取所有启用方向的 topics」，即 M3 就需要方向词表；
  - M4.2 的多语言关键词也从词表读取；
  - M4.4 第 2 条写道「方向在初筛阶段用 topics 和描述做一次快速分类，M5 实现前全部视为同一方向」，这与 M3.7 的发现逻辑互相矛盾（发现阶段没有 topics 就无法查询）。
- **建议 A**：M3 就创建 `collector\方向词表.json`，按附录 D 的表格填入 `domain`、`topics`、`prerequisites`；`keywords` 暂留空数组，M4 补全；M5 只实现分类、覆盖与学习模式逻辑。
- **理由**：
  - 附录 D 已经给出完整的 topics 清单，填入不需要新的设计决定；
  - 发现阶段确实依赖 topics，把它放在 M3 能让 M3 独立运行与验收；
  - M3、M4、M5 的边界更清楚：词表数据在 M3 出现，关键词在 M4 补全，分类逻辑在 M5 实现。
  - 不推荐的替代做法：把 topics 硬编码在 `discover.py` 中，M5 再迁移到词表，会形成两份来源，容易不同步。
- **状态**：待决定（Q1）。

### P3b 同类问题：M3 依赖 M5 的复收规则（优先级：中，需决定 Q3）

- **现象**：M3.7 的候选过滤写道「`status=questioned` 且不满足复收条件（M5.4）则丢弃」；复收条件（含 update 模式的 release 主版本比较与 gain 倍数）定义在 M5.4，依赖的 `release` 与 `gain_at_first_pack` 数据在 M3 阶段也未就绪。
- **建议**：M3 中，`status=questioned` 的仓库**一律跳过**，并在 `discover.py` 中预留一个 `should_revisit(repo)` 函数，只返回 False；M5 实现完整规则。
- **理由**：保守做法不会误入包；不影响 M3 验收用例 6（14 天内已入包不再入包）与 M5 验收用例 7（未满复收天数不入包）。
- **状态**：待决定（Q3）。

### P4 热度分冷启动（优先级：高，需决定 Q2）

- **现象**：
  - `heat_score = (ln(1+gain/days) − m) / (1.4826 × s)`，其中 m 与 s 来自近 60 天的 `candidate_gains` 历史（M4.3）；
  - 首次运行时历史为空，样本数远小于 `min_group_samples`（30），合并基线也为空，m 没有定义；
  - 但 M3.5 第 7 步要求「初筛 → 选入」，M4.4 第 1 条以 `heat_score ≥ 1.0` 过滤；
  - 方案 2.6 节规定 `heat_score` 的类型是 `float`，不允许为空。
- **建议 B**：历史样本不足（合并后仍低于 `min_group_samples`）时：
  1. 热度分不计算，入选门槛只用 `stars_gained_window ≥ min_gain_window`；
  2. 按「窗口新增 ÷ 天数」降序排序，同方向不超过 `per_direction_cap`；
  3. 采集包中 `heat_score` 写 `null`，`run.gap_note` 注明「冷启动：热度分未启用」；
  4. 样本积累够后自动切换到 M4.3 的公式。
  - 同时需要修改方案 2.6 节：把 `heat_score` 的类型改为「float 或 null」。
- **理由**：
  - 不引入任意的先验参数；
  - 与 M4.3 已有的 fallback 思路一致，只是更早触发；
  - 保证 M3 可以独立运行和验收，而不是等 M4 才能跑。
- **不推荐的替代做法**：用固定常数充当先验（例如假设 m=0）。没有依据，会让第一批结果的排序失真。
- **状态**：待决定（Q2）。

  3. 若接口返回 404/410，按方案退化为「快照差值估算」，并在 `gap_note` 注明。
- **理由**：不能凭记忆假定周起始日或时区；先写解析逻辑，真实数据到了再校验，影响范围最小。

### 9.7 M3 开发中的解释确认（2026-10-10）

| # | 问题 | 结论 |
|---|---|---|
| a | 窗口含两端，7 天窗口有 8 个日期 | **不改**。Star 历史只有按天的数据，精确到小时做不到。首尾两天各算一次是已知效果：每个采集包只用于本次排序，不会跨包累加。唯一要求：计算日均新增时，分母用 `len(star_days)`（即 8），不要用 7，分子分母口径一致 |
| b | 每个查询只取 1 页（100 条），却要求「取前 1000 条」 | **保持 1 页，不翻页**。按 Star 降序取前 100 条就是本意；`max_candidates=200`，不需要全量。方案中「取前 1000 条」理解为「接受截断、不再细分」，`truncated` 的含义改为：单日仍超过 1000 条、无法再拆分。按日期拆分仍按原规则执行，它的作用是让窗口里较新的日子也有机会进入前 100。每次查询把 `total_count` 写进日志，便于以后检查覆盖面 |
| c | `--since` 是否推进水位线 | **同意你的做法**：起点为该日 00:00 UTC，成功后照常推进。补充规则：水位线**只前进不后退**，推进时取 `max(原水位线, 窗口终点)`。那句「不推进水位线以外的状态」作废，入包状态等照常更新 |

对「自行决定」各点的意见：

| 点 | 意见 |
|---|---|
| `source_repos` 用 `GET /repos/{full_name}` 得到 repo_id | 同意，但**先查 `repos` 表的 `full_name`**，查不到才调接口，避免每次运行都为所有已出题仓库重复请求。仓库改名时接口会重定向，以返回的 `id` 为准，并更新 `full_name` |
| Star 快照存在 `meta` 表 | **改为新建 `snapshots` 表**：`repo_id INT, taken_at TEXT, stars INT, PK(repo_id, taken_at)`，只追加不覆盖。理由：远期的热度预测模型要用连续快照，`meta` 里一个键只能存最新一次，会丢历史。新增表不影响现有表结构 |
| 未预期错误用退出码 1 | 同意。同时 `runs` 记 `failed`、写日志、水位线不动；定时任务用 `pythonw` 运行，不能弹窗 |
| `run_id` 用运行时间 | 同意，格式与方案示例一致，如 `20261010T032726Z` |
| 英文版 README 只要存在就抓 | 同意。M3 阶段 `doc_lang` 还是 `und`，无法判断主文档语言；M4 识别出主文档是英语时，`readme_en_sections` 写 null |

### 9.9 M4 开发中的确认（2026-10-10）

**依赖**：同意安装 `fast-langdetect`。要求：只用它自带的小模型（lite / 低内存模式），**运行时不得联网下载模型**（完整模型从境外地址下载，回国后很可能下不了）。请在代码注释和 `requirements.txt` 中写明；安装或加载失败时退回 `langdetect`。

**对实现判断的意见**

| 判断 | 意见 |
|---|---|
| 文字系统 40–199 字 `medium`、≥200 字 `high`；假名至少 3 个 | 同意 |
| 关键词轮换断点只在出包成功后保存；失败运行删除本次 `candidate_gains` | 同意 |
| 窗口为空时连发现也跳过 | 同意，并补充：不出包，`runs` 记 `skipped_recent`、`note` 写「窗口不足一天」，**水位线不推进**（下次窗口从原起点算起，不会漏） |
| 初筛按描述定语言组进入基线，深采后不回改基线 | 同意不回改基线。但有一个影响 D3 的问题，见下 |
| 方向上限 M5 才执行 | 同意 |

**D3 风险：只看描述会把大量中文项目算成英语组。**很多中文作者的仓库描述用英文、README 用中文（例如首包里的 `Panniantong/Agent-Reach`）。初筛只看描述，这类项目会进入英语组，和英语大项目比热度，正好违背 D3。
处理：初筛时，对通过 `min_gain_window` 的候选额外取一次 README（`GET /repos/{o}/{r}/readme`，只用清洗后前 3000 字），用「描述 + README」识别语言组。最多 200 次调用，在限额内。取到的 README 写入 `enrich_cache`，深采时直接复用，不重复请求。M4 验收用例中补一条：描述为英文、README 为中文的候选，语言组为 `zh`。

**方向词表关键词的修改规则**（多语言关键词的用途是找到**该语言的**项目；只要关键词本身是英文或各语言通用写法，搜出来的就主要是英语项目，白白消耗搜索次数）：

1. 非英语关键词必须含该语言特有的文字或词，不能是纯英文或缩写。据此修改：
   - `zh` 的 `MCP` → `MCP 服务`、`MCP 工具`
   - `fr` 的 `fine-tuning` → 留空
   - `es/fr/de/pt` 的 `multimodal` → `modelos multimodales`、`modèles multimodaux`、`multimodale Modelle`、`modelos multimodais`
2. 各语言之间完全相同的关键词只保留一个语言（避免同一查询执行两遍）：`framework de agentes`、`sistemas multiagente`、`LLM local` 只保留在 `es`，`pt` 改为 `framework de agentes de IA`、`sistemas multiagentes`、`rodar LLM localmente`；`fr` 的 `LLM local` 改为 `LLM en local`。
3. `mcp-tools` 的其他语言补上：`ja` `MCPサーバー`，`ko` `MCP 서버`，`ru` `MCP-сервер`；`es/fr/de/pt` 留空即可。
4. 补充覆盖面更广的中日文通用词：`agent-framework` 的 `zh` 加 `智能体`，`ja` 加 `エージェント`。
5. 过宽的中文词去掉或收窄：`知识库` → `RAG 知识库`，`数据集` → `合成数据集`，`本地部署` → `大模型本地部署`。
6. 多词关键词在查询中用英文双引号括起来，按短语匹配。
7. 用户首次带 Token 真实运行后，看日志里每个关键词的 `total_count`：长期为 0 或经常超过 1000 的关键词再替换。这一步留给用户人工调整，不需要写成代码。

### 9.10 M5 开发中的确认（2026-10-10）

| # | Haiku 的判断 | 结论 |
|---|---|---|
| 1 | 复收的版本判断只对窗口新增 ≥ `min_gain_window` 的候选生效 | **同意，作为明确决定**：「出了新主版本，且有人关注」才值得重新出题；对所有已出题仓库逐个查 release 会随题库增长不断增加调用。效果上 M5.4 变为「新主版本且窗口新增 ≥ 20」或「增长翻倍」 |
| 2 | 题库里的已出题仓库没有 `gain_at_first_pack`，「增长 2 倍」规则不生效 | **补基线 + 改口径**：① `gain_at_first_pack` 为空时，用该仓库**第一次再被观察到**时的数值补上（这一次不据此复收）；② 窗口长度每次不同（首次 7 天、之后约 1 天），比较原始增量没有意义，改为比较**日均新增**（`gain ÷ len(star_days)`）。字段语义改为「首次记录时的日均新增」，名称可保留，代码注释写明 |
| 3 | 增长触发的复收，`release_change` 为 null | **改为**：只要最新 release 的 tag 与上次记录的不同，就填 `release_change`（不论是否是主版本变化），供出题参考；tag 没变才为 null。`mode_reason` 写明触发原因是增长 |
| 4 | 方向上限用快速分类，深采后方向可能变化 | 同意（即 9.2 的 P9 设计）。深采后方向变化不再回头调整入包名单 |
| 5 | 没有对比项目时，依赖和目录差异为空列表，不加备注 | **加备注**：`compared_with` 为空时，`note` 写「本方向尚无已出题项目可对比，请参考 题库目录.md 中同领域的题目判断差异」；对比项目存在但无缓存时，仍按方案写「对比项目无缓存数据」。理由：题库重建后，很多方向会出现前置概念已出题、却没有关联仓库的情况，没有备注的话，出题 AI 会以为差异为空 |
| 6 | 单个项目失败就跳过它（退出码 0），连续 3 次网络失败才返回退出码 3 | 同意。补充：被跳过的项目保持 `seen` 状态（不能标为 `packed`），下次运行自动重试；`runs.note` 记录跳过的个数，预览 Markdown 末尾列出被跳过的仓库 |
